# Figma File Organization

Follow [Brix](../../AGENT.md) and [construction standards](../figma-design-standards/SKILL.md). This responsibility plans destinations; the designer writes nodes. Use the same shared before/after pass, not an organization audit round.

## Destinations

Use the selected Figma file's actual scoped structure and existing mappings. Reuse destinations by purpose/content, preserving naming. Create only requested surfaces/roles, e.g. `App / Customer`, `Web / Public`, `Dashboard / Admin`, `Components`. These are examples, not pages to scaffold. Separate product surfaces without duplicating the shared identity/components.

Create each page/container only with its first actual content; do not count empty frames/headings as delivery. A planned destination remains a record until ready. Add `Trash` only with an authorized retired item.

## Parent-first construction

Resolve destination → configured content Frame → required group → screen/component before populating content. A Page is not an Auto Layout Frame, and a Section is not a substitute. A low-level tool may attach an empty node immediately after creation before population. Never build a finished design elsewhere and move it into a wrapper. If the adapter cannot support this, disclose the capability gap.

Use a primary Auto Layout content Frame for new or explicitly organized pages. Group real screens by flow and components by family. Keep each screen's dimensions, native editability, prototypes and export identity; the outer board must not stretch or clip screens. Preserve genuine component sets/variants. Canvas spacing may be a justified one-off instead of a product token. Build main components in their intended family destination and instances in screens.

Record actual parent IDs and ordered creation/attachment/population evidence by reference to operations. Transient empty parents during a supported batch are not atomicity claims or completed content. A small edit does not authorize wrapping or moving the whole existing page.

## Scoped moves and recovery

Reorganization, archive and restore may move pre-existing content only within authorization. Before moving shared definitions or linked screens, use current dependency evidence to avoid breaking instances/prototypes. Do not detach to archive. Trash retains original parent/page/order, IDs, reason and replacement link; no automatic purge or unsolicited obsolete-content classification.

After an interrupted creation, inspect only uncertain state before retrying. Complete the intended content where possible. Remove a task-created empty destination only if ownership, emptiness and absence of user work/dependencies are confirmed; otherwise retain it as incomplete. Restore from recorded location, resolving missing parents honestly.

## Record

Keep one organization section/record with intended first content, existing/planned destinations, operations, actual resulting IDs and recovery data. The plan becomes actual mapping through targeted updates, not a copied second report. Link shared pass criteria for nonempty content, Auto Layout, screen/component integrity and prototype/export preservation. File organization is complete only from actual results, not names alone.
