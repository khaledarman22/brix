# Visual execution

Use this protocol within the current task/part for composed screens or material visual changes. Small corrections stay scoped. Existing reference choices and research skips remain valid.

Before this pass, resume or establish [the project composition language](project-composition.md). Its own rendered examples are the primary continuity anchors; outside references inform unresolved aspects rather than prescribe each screen.

## See and decide

Directly view the selected original image/version and relevant crop at legible resolution. For existing work, also view the destination baseline. Reuse images already inspected in the current working context; after a handoff or context loss, reopen them from saved evidence. A URL, node tree, rating, or prose description is not visual inspection. If an image cannot be viewed, record that limitation and restore access before claiming reference fidelity; continue independent work where possible.

Record a short visual decision note in the existing local task/part checkpoint: source version/crop, baseline evidence, focal point and reading order, image-to-text proportions, title width/wrapping, spacing/grouping, and intended adaptations to product identity/content. Include only decisions relevant to the scope. Distinguish observed measurements from estimates. Explain what is retained, what changes, and why; do not substitute a generic component inventory for composition decisions.

When direction is genuinely unresolved, quick visual alternatives may help. Use only as many as the decision needs. Image generation is optional art-direction exploration, not a required intermediary or proof that a UI works. Preserve explicit user selections; otherwise compare the actual alternatives visually and choose the one best suited to this project's task, content and identity, recording the rationale. Present options and wait only when the user explicitly requested that choice. Do not restart selection for ordinary execution refinements.

## Construct

Build native editable Figma content using the project composition language, screen function and actual identity, components, text and target dimensions. Honor explicitly requested reference compositions within their scope. Keep the original visual evidence available during construction rather than reconstructing solely from the note. Respect RTL, realistic text lengths and required viewport constraints. Adapt deliberate differences explicitly rather than copying reference branding or forcing pixel equality across different content.

Resolve important imagery with authorized assets when within scope. If assets are unavailable, identify placeholders and use the image-prompts workflow for required prompts. A saved prompt is not an image. Do not claim finished visual quality for an image-led composition with missing images; explain which conclusions remain provisional. Never use a generated complete-interface image as the editable product screen.

## Inspect and correct

At a meaningful composition boundary, export and actually view the changed scope with enough surrounding context to assess integration. This is the normal composition review, not an extra audit. Compare it visually with the project language and its rendered anchors, plus any explicitly requested reference aspects, and with the baseline when improving existing work. Judge both fidelity and independent quality: focal hierarchy, balance, typography/wrapping, image crop, spacing, readability and identity. Token compliance alone is insufficient.

Identify concrete mismatches and apply targeted corrections. Inspect a fresh export after relevant corrections; do not repeat screenshots of unchanged work or inspect every primitive. Stop when the scoped criteria pass. If a defect persists without a justified new fix, record the blocker and next action instead of cycling or claiming success.

Separate possible causes using observed evidence: composition decisions, missing assets, implementation choices, or documented tool limitations. A good generated picture and a weak Figma result do not by themselves prove tool incapability. Inspect the relevant nodes/API behavior before assigning that cause.

Save the source/version, destination IDs, visual decision note, baseline/final evidence references, observed improvements, intentional differences and remaining issues in the same task/part checkpoint. Use existing flexible checkpoint fields; no new cache schema or separate review queue is needed. Completion requires an actually inspected current result; report unavailable visual checks honestly.

## First trial

When asked to test this workflow, use one authorized existing section with a known reference/direction and real content. Save its baseline, apply the protocol, then return before/after evidence with concrete changes and limitations. Broader rollout follows observed results, not an automatic whole-screen redesign.
